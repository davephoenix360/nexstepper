Nexstepper — Architecture & Infrastructure Review

A ground-level read of the system Nexstepper actually runs today: what it is built on, how each major feature is put together, which decisions were load-bearing, and where the seams are showing. Diagrams are inline SVG — this file opens offline with no CDN.

Status since publication — read this first

The verdict

Bottom line

Nexstepper is under-built relative to how well it is documented. The architecture is coherent, the domain model is unusually thoughtful for a solo-founder SaaS, and the decision record is better than most teams of ten produce. The problem is not the design — it is that the last 20% of every feature (the surface that reads the data, the CI gate that proves the routes compile, the ops promise in the runbook) is repeatedly thinner than the core it supports. Several services the runbook, the pricing page and the plan constants treat as live are scaffolds.

The three things worth saying out loud:

  1. The scoring engine is the product, and it is the strongest thing in the repo. A two-engine design (deterministic token/BM25 baseline + a hybrid engine with semantic embeddings and probability-weighted "Jev" evaluation) that composes through one shared function, with a hand-labelled validation corpus and a Pearson-r gate, is real engineering. This is not a wrapper around an LLM.
  2. One scoring dimension is dead weight. Role Fit is a constant 50 for every resume in every production path — a fixed 5 points of 100 that no candidate can move. The function that would compute it exists and is tested; nothing in production calls it.
  3. The failure mode of this codebase is not a crash — it is a number that disagrees with itself. The history is visible in the drift memos: the list badge vs the scorecard, the scorecard tips vs the score, the recompute flicker. The resolveRenderedBreakdown helper was the right cure for the first one; the same cure has not been applied to the two remaining paths where a score is computed independently of the snapshot the UI renders from.

What is genuinely strong

The domain model

17 tables, no Postgres enums (every enum is a text column plus an app-layer union — cheaper to evolve than a migration per state). The resume is an append-only revision chain with a currentRevisionId pointer, which gives undo, audit and future collab for free. The share token is a deterministic HMAC, so enabling sharing is idempotent and the owner can always re-derive their own URL without the raw link ever being stored. The chat_usage composite primary key is explicitly documented as load-bearing for ON CONFLICT — that is the kind of comment that usually only appears after it has broken.

The AI cost & reliability engineering

Model selection is centralised in one file with explicit fallback chains, and the chains are ordered by measured reliability rather than price — a probe (tests/unit/ai/chat-tool-call-probe.test.ts) runs the real agent loop with the real tool schemas, unforced, five attempts per model. That probe also caught a probe bug: the first version passed parameters where AI SDK 6 wants inputSchema, which silently made tools schemaless and produced confidently wrong rankings. Free users are routed to a $0-only model chain so a free account can never cost money.

Failure-mode thinking

The rich-text overlay refuses to touch the stored text — a mark is a path-addressed overlay, and a mark that cannot be re-anchored is dropped, never misapplied. The ATS score is asserted deeply equal with and without formatting. The chat route builds every header through one helper that forces ASCII-safety, because the previous version let a Unicode ellipsis in a session title 500 every turn in that thread. Loss of a bold is cosmetic; bolding the wrong words is a lie.

Operational maturity

An 800-line production runbook with a 16-step smoke test, a five-scenario rollback playbook, two separate Neon projects (prod and dev — not branches), GDPR Art. 17/20 export and Art. 17 erasure with a non-reversible hashed audit log, and a GitHub-issue feedback pipeline that degrades to a local row when the token is absent. A stripe_events_processed idempotency log marks events after success, so transient failures still retry.

Method and limits

Every claim below is sourced as path:line. The review was produced by static reading plus targeted greps; the app was not run and the test suite was not executed, so anything marked "read from source" carries the usual static-analysis caveat — code that is unreachable from a route could still be reachable from a script. The `.env` files were deliberately not inspected (secrets), which means live deployment state is inferred from the runbook and the migrations directory, not observed. Where the tree and the documentation disagree, both are reported; the disagreement is itself a finding.

2. System context

Nexstepper is a single Next.js 16 application deployed to Vercel. It is not a monorepo and not a microservices system: there is exactly one deployable unit, five API routes, and a set of managed third parties. Every diagram in this document is drawn from that reality.

Topology decisions worth keeping

Two Neon projects
Production and local development are separate Neon projects, not one project with branches. Running pnpm db:migrate locally touches the dev project only; production migrations land when the commit reaches main and Vercel's prebuild runs db:migrate. The consequence — schema changes are live in dev long before prod, and a bad migration fails in dev first — is documented and accepted.
One driver
postgres-js only, prepare: false for serverless (lib/db/drizzle.ts:16-29). The AGENTS.md phrase "driver auto-detected" is wrong — there is no auto-detection.
Canonical host
www.nexstepper.com, with the apex 308-redirecting. Because of that redirect, lib/auth.ts carries an explicit trustedOrigins list, and any new OAuth callback must register both hosts.
No middleware
There is no Next middleware file; route protection is done per-route via getUser() in the dashboard layout and per-action via requirePro() / requireAuth(). Simple and readable, but every new route has to remember to do it.
Print, not PDF service
PDF export is the browser's own print dialog (ADR 0002). No managed PDF API, no Playwright on the hot path — the resume's PII never leaves the user's machine. Server-side PDF generation is explicitly deferred.

5. Feature-by-feature

The core loop the product is built around: master → JD parse → score → fix → share. Each stage below states what it does, how it is built, the decision that shaped it, and where it is thin.

Master resume→ Parse a JD→ Score it→ Fix in place→ Share a link→ Reviews & collab (not built)

5.1 Master resume, editor and persistence

How it works

The editor (components/editable/editable-resume.tsx) is a single client component wrapping the template in a React Hook Form FormProvider, with zodResolver(resumeDataSchema) and mode: 'onSubmit' so typing is never interrupted by validation errors. The schema source of truth is lib/resume-schema/ — 13 section schemas aggregated into resumeSectionsSchema, JSON Resume v1.0.0-compatible.

Three details that matter more than they look:

  • Server data is pushed back with form.reset(), not defaultValues. RHF reads defaultValues once; without the reset, the editor showed stale content after a chat rewrite.
  • Undo history lives in localStorage (nexstepper:history:<resumeId>, 50 entries), not the server. It is per-device and is lost on a different browser; the server-side revision chain is the durable one, but nothing surfaces it in the UI.
  • Autosave is a 1500 ms debounce that compares a serialised snapshot of watched values, with the effect depending on the serialised string rather than the field list — otherwise a field that depends on another starves the loop.

Persistence is via server actions (saveResumeAction, autosaveResumeAction) followed by router.refresh(). There is no optimistic UI — the save button goes pending and the page re-fetches. For a 1,500 ms debounced autosave of a JSONB envelope that is defensible; for the chat tool's edits, which land via a different path, it is worth re-examining.

Decisions and seams

GoodOne schema (Zod) validates the client form, the server action and the AI's structured output. The template id is watched from the form, so the gallery can switch templates without a reload. Drag-to-reorder mounts DndContext only in the editable path, and only the grip handle carries listeners — so click-to-edit still works.
ThinrestoreRevision and listRevisions exist in the query layer and have no callers anywhere. The revision history the schema was designed around is unreachable in the product.

5.2 Resume import

Pipeline: file → text extraction → LLM → envelope → first revision.

  • PDF via unpdf with mergePages: true; DOCX via mammoth extractRawText; TXT as UTF-8 with BOM stripped. Legacy .doc is explicitly unsupported.
  • Guards: MAX_FILE_BYTES = 10 MB, MIN_TEXT_LENGTH = 100, and typed error codes (unsupported_type | empty_file | pdf_parse_failed | docx_parse_failed | text_too_short).
  • The Next config raises serverActions.bodySizeLimit to 10 MB to match; the server-side cap is the real guard.
  • A global 180-second cap spans the whole chain, because per-model 90s × 4 fallback models would exceed the Server Action's maxDuration and return a 499. That is a good catch that is easy to miss.
Note

The parse output is not a score input. It populates the envelope; the deterministic and hybrid engines then score the text that results. Keeping those two steps separate is what allows the same scoring path to serve imported, typed and AI-written resumes identically.

5.3 Job description parsing and intent extraction

Two separate AI calls, which is the key design decision:

  1. Structured parse (parseJd) → parsedJdSchema: title, company, seniority, location, salary, skills, responsibilities, qualifications, years. Minimum 50 characters; 90-second per-call timeout; temperature: 0. Rejects with no_api_key when the gateway key is absent.
  2. Intent extraction (extractJdIntent) → the v2 prioritisation: mustHaveSkills / niceToHaveSkills / implicitSkills. Bounded at 16,000 characters in, 2,000 tokens out, 30-second timeout.

The intent extractor's classification rules are worth reading: a section header is the strongest signal; hedged language ("is a plus") means nice-to-have; unlabelled responsibility bullets are neither; implicit skills are rare (roughly 70% of JDs yield none); years are a floor, not a target. That conservatism matters — it is what stops the engine from penalising a resume for skills the posting never asked for.

The persisted envelope is jobPostingSchema, which is a superset of the parse output: it adds description, requirements, niceToHaves, benefits, source, capturedAt and the Markdown rendering. Two schemas for "a job posting" is slightly awkward, but the parse shape is the model's contract and the envelope is the product's — keeping them separate is right.

5.4 Variant creation

A variant is not a new entity: it is a row in resumes with is_master = false and parent_resume_id pointing at the master. Content lives in the same revision chain. This is why resume_variants (the join table with matchScore) turned out to be unnecessary — and why it is now orphaned.

The UI path is paste a JD → create variant from JD: the JD is parsed, the intent extracted, a new resumes row is created pointing at the master, and the editor opens on it with the JD in the right rail. applications has a complete query layer and an actions file at app/(dashboard)/dashboard/applications/actions.ts, but no page renders it.

Decision needed

Either the applications pipeline gets a UI (an "Applications" board — job title, company, status, applied date, notes) or the two tables and their query layer are deleted. Right now they are a third path through the domain that nothing exercises, and they are the source of two of the findings in §9.

5.5 The ATS scoring engine

This is the core of the product, so it gets the most detail. It is the strongest subsystem in the repository and the one with the most consequential defects.

The dimensions and their weights

Two weight sets, selected by whether the JD has v2 intent data (useV2Weights = !intentCoverageBreakdown.fallback). Both sum to 1.00. Under v1 weights the three v2 dimensions carry zero weight, so their neutral 50s contribute nothing.

What "Jev" actually is

Worth stating precisely because the name invites a wrong assumption: Jev is TypeSafe's probabilistic judgment API, not a model hosted by Nexstepper. It is reached through the same Vercel AI Gateway, with the provider pinned to typesafe-ai for zero data retention (the code throws if the resolved provider differs). The model id is version-pinned (jev-1.14.0) so scores cannot drift silently.

Requirement evaluation is two calls: the first classifies each JD entry as a genuine skill and as an eligibility gate; the second asks for evidence depth 0–3. Gates (a degree, an English-proficiency requirement) are excluded from scoring — nobody closes a degree gate by rewording a bullet. The arithmetic is 100 × (0.5·coverage + 0.5·depth) with an evidence threshold of 0.5, not 1.0, because probability-weighted mass straddles the levels. Cost is roughly $0.0002 per evaluation at ~250 ms per call.

Where the Jev verdict becomes a number: the hybrid engine runs Jev in parallel with the deterministic baseline, then substitutes only the affected sub-scores before composing. A Jev failure returns ok: false and the token-based scores are kept — the engine degrades to the deterministic path rather than throwing.

Finding — Role Fit is a constant

lib/scoring-async/score-hybrid.ts:93-100 calls the sync engine with { roleFitSimilarity: null }; the engine then returns NEUTRAL_ROLE_FIT_SCORE = 50 with fallback: true. The async implementation roleFitSimilarity() exists and works, but a repo-wide search finds it called only from tests. The sync path defaults to null as well.

Consequence: under v2 weights every resume receives a fixed 0.10 × 50 = 5.0 points from Role Fit. The scorecard shows a flat bar for one of seven dimensions, and no candidate can move it. This is also why docs/plans/demo-video.md ("Role fit moves off 50") is unfilmable, as the drift memo records.

Snapshots and the "one helper, both surfaces" rule

resolveRenderedBreakdown({persisted, compute}) returns the persisted breakdown when it is a finite score with dimensions and criteria; otherwise it computes. It exists to stop a specific bug: the Recompute button runs the hybrid engine, revalidatePath re-renders the RSC, and the page used to recompute with the sync engine — so the enhanced number flashed and was replaced by the older token-based one. Three call sites use it today: the variant page, the resume list, and the seed script. The list uses a batched getLatestScoreSnapshots (SELECT DISTINCT ON (resume_id) … ORDER BY created_at DESC) so a list of 50 resumes costs one query, not 50.

The tips, meanwhile, read the score's own values: the keyword tip uses breakdown.jevRequirements?.missing when Jev ran, the Intent Coverage tip renders the score's own miss list, and the ATS Similarity tip reads criteriaScores['ATS Similarity']. That was the fix for the 2026-11-02 incident where the score said "nothing missing" while the tip under the same number said "missing 4 must-have skills" — two of which the resume demonstrably covered.

5.6 The inline issue surface

The scorecard is a funnel; the editor is the fix surface. Clicking a weak dimension bar opens a popover anchored to the actual field in the resume, and (for Pro) offers an AI rewrite that is applied in place.

  • Criterion → field path: dimension-level criteria map to sections.work[0].positions[0].title; skill misses map to sections.skills[0].keywords[0]. The .positions[0] segment is mandatory — bullets live inside positions, not directly under the work entry. This is exactly the kind of detail that silently breaks a mapping.
  • The rewrite prompt asks for exactly three rewrites, 1–2 sentences, with the JD's and the resume's vocabulary passed as explicit allow-lists and a hard prohibition on introducing new tools, metrics or employers. Vocabulary lists are capped (60 allow-list terms, 80 extracted).
  • The apply bridge is a one-shot typed CustomEvent on window carrying {path, text}. The editor handles it with form.setValue → handleSubmit → recomputeScoreAction. The whole plan is applied with one write so Ctrl+Z undoes it in a single step.
  • The tier gate lives at the server-action boundary (ADR 0006/0007): Free users see the tip without the popover; Pro is enforced server-side by requirePro(), with the client hint purely cosmetic.

The design rationale is documented well: Optimize v0 was retired because it pulled the user out of the editor they were actively editing, and this replacement never does. It also never marks an eligibility gate, never marks a line that does not name a genuine skill, and never marks a skill the resume does not evidence — a posting whose five requirements were all non-skills produces the honest answer, "this posting doesn't name skills your resume lists."

5.7 The chat agent ("Scout")

Mechanics

streamText with stopWhen: stepCountIs(6), maxOutputTokens: 8000, temperature: 0.3, streaming over SSE. The system prompt is ~757 lines and rebuilds the resume as text every turn, injects the ATS context (dimension scores plus the missed must/nice/implicit lists), and runs the JD through sanitizeUntrusted — closing tags defanged, C0 controls stripped, Unicode tag blocks and zero-width/bidi characters removed, JD description truncated to 4,000 characters and requirement lists to 10 each. Prompt injection from a pasted job description is treated as a first-class threat. Good.

The measurement artefacts

page-fit.generated.ts and section-space.generated.ts are not model output — they are produced by headless-Chrome measurement scripts and committed, with an honest accuracy column ("27/27"). Section figures are deltas in inches versus the same resume with that section hidden. When no formula exists, the estimator returns null rather than a guess. That is the right default for a number a user might act on.

Cost control

Two independent gates, both in the DB. The turn counter is consumed atomically via INSERT … ON CONFLICT; the token counter is written after the stream drains, which is a deliberate soft cap — a user can overshoot by roughly one turn, but the row lock is not held across a multi-second model call. The 429 message distinguishes the two cases: "You've used today's free AI allowance" (token cap) versus "Daily limit reached" (turn limit), because the turn limit may be infinite and "daily limit reached" would then be misleading.

5.8 Templates, rendering and print

  • Six templates, code-driven (classic, modern, minimal, executive, creative, jake) in components/resume-templates/index.ts. The DB stores only the id — there is no templates table and no admin authoring surface, so the "template studio" in the product vision does not exist yet.
  • One registry renders every surface: editor, preview and share all call getTemplate(data.template). The Field* helpers swap between the RHF-bound editable components and a plain read-only branch on mode.editable — the same pattern as the rich-text renderer, and the reason the editor and the share link cannot disagree.
  • Print is the browser's own dialog (lib/print/safe-print.ts calls window.print() synchronously inside the click handler — a Safari requirement — and returns a platform-tagged result so the UI can give iPhone/iPad/Mac-specific guidance). Print CSS lives in app/globals.css, with a .printable-root isolation layer that hides the dashboard chrome.
Stale ADR

ADR 0002 describes the flow as "the preview page auto-runs window.print() on mount via ?print=1". The preview page's own docstring says printing "moved to the editor's one-click Print button", and the page exposes no print button. The ADR documents a flow that no longer exists. (Also: the template gallery modal's docstring says "Five templates today"; there are six.)

5.9 The rich-text overlay

This is the best single design decision in the repository, and it is worth understanding why.

The resume's text is load-bearing across the whole product: the scoring engine reads it, the BM25 tokenizer reads it, the page-fit estimator measures it, the AI's edit-matching matches against it, the parsers produce it, and the GDPR export hands it to the user. If markup entered the stored strings, every one of those consumers would change behaviour at once and the scores users had already seen would stop meaning what they meant.

So formatting is an overlay: an envelope-level formatting map keyed by the same dotted paths RHF uses, each span carrying start, the literal text it covers, and its marks. Resolution re-anchors each span — exact hit, else closest occurrence, else dropped. The failure mode is a missing bold, never a wrong bold. A test asserts the score breakdown is deeply equal with and without marks.

Two consequences worth noting: "Highlight this job's skills" writes the entire overlay in one setValue, so Ctrl+Z undoes it in one step; and because the stored text never changes, the ATS score genuinely does not move when a candidate emphasises something — which the toolbar states plainly, because a user who believes decoration buys points will be disappointed later.

5.10 Public sharing

/r/{token} is a public route outside the dashboard group, with no auth — the token is the capability. A disabled link and an unknown token both 404. The page is noindex, nofollow, and the view counter increments in a fire-and-forget call whose errors are swallowed, so a counter failure can never break a public render.

The token is deterministic: base64url(HMAC-SHA256(SHARE_LINK_SECRET, resume_id)[:16]), ~22 characters. That means enabling sharing is idempotent, the same resume always renders at the same URL, and the owner can re-read their own link forever by recomputing it — without the raw URL ever being stored. It also means rotating the secret invalidates every existing link, which is documented as the intended blast radius.

Legacy 64-character hex tokens are still accepted, so links created before the redesign keep working. One small detail: the share-status view object is hand-built in two places (the variant page and the preview page) while the canonical type lives in the share button component — three declarations of one shape.

5.11 Auth, billing and quota

Authentication

Better Auth with the Drizzle adapter. Plugins: nextCookies() plus three separate captcha() instances, one per surface, each with its own expectedAction and a disjoint endpoint list (/sign-up/email, /sign-in/email, /request-password-reset) — Better Auth runs every plugin's onRequest hook and each decides for itself, so a token minted on the sign-up widget cannot be replayed at sign-in.

The Turnstile site key is deliberately not a NEXT_PUBLIC_* variable. Public env vars are baked in at build time, so on Vercel a preview build and its runtime can disagree about whether the widget exists — and a server demanding a token the client cannot produce locks everyone out. Reading it server-side and passing it down keeps the widget and the gate decided by the same read in the same request. The check fails open when half-configured, so a deployment missing one variable still signs users up, and says so loudly in the boot log.

Sessions are DB-backed: 24-hour expiry, 24-hour refresh age, 5-minute cookie cache. There is no email-verification flow (the field exists but stays false for local signups) and Google sign-in is opt-in — set both variables or neither; a half-set pair disables the provider rather than crashing.

Billing

Stripe Checkout in subscription mode with a 7-day trial. The idempotency key is userId:priceId:minute-bucket, which collapses double-clicks while still allowing an intentional re-purchase a minute later. The webhook handles customer.subscription.created|updated|deleted; ten invoice/setup/checkout events are explicit no-ops so the default branch stays useful for catching genuinely unknown event types. The plan is mirrored into subscriptions, and upgrade/downgrade analytics fire only on transitions, not on every reconciliation.

Two hard-won behaviours: a missing local subscription row throws LocalSubscriptionNotFoundError and returns 500 so Stripe retries (the checkout-success redirect can lose the race), with a per-customer retry cap of 5 so a genuinely unknown customer does not burn Stripe's three-day retry window; and the event is marked processed after the work succeeds, so transient failures still retry.

The tier gate

ADR 0007 layers it: requirePro() is the server-authoritative gate and throws ProRequiredError; the client hook is cosmetic only, and the plan is passed as a prop so the UI cannot flicker from Pro to "Upgrade" mid-session. isProEffective requires plan === 'pro' and status ∈ {active, trialing} — trials count, past-due does not, and Stripe's status is trusted rather than double-gated on currentPeriodEnd.

5.12 Observability and consent

Sentry is wired across four configs with DSN guarding. The client and edge configs carry a full dataCollection hardening block — denying forwarded/-ip/remote-/via/-user headers, cookies and query parameters, with genAI: {inputs:false, outputs:false} and databaseQueryData: false. The server config hardens only userInfo: false; the rest is deliberately deferred with a comment saying so. Build-time sourcemap upload is gated on SENTRY_AUTH_TOKEN so dev builds do not emit noisy warnings.

PostHog runs server-side with a 1-second flush interval so analytics never blocks a request, and a typed event catalogue of 25 named events with property bags. AI calls are wrapped in @posthog/ai withTracing, with the persisted chat session id as the AI session id and posthogPrivacyMode: true so resume PII and pasted job descriptions never reach a second processor.

Consent is framework-free and lives in lib/consent.ts: four categories, essential exempt, the decision stored in localStorage rather than a cookie, versioned by CONSENT_VERSION so adding a category re-prompts, GPC honoured, and every stored field treated as untrusted on parse. Both analytics gates — PostHog and Vercel Web Analytics — use one predicate: hasDecidedConsent && consent.analytics === true.

Honest caveat, already documented in-repo

PostHog runs with capture_pageview: false because there is no SPA route-change listener, so Vercel Web Analytics covers page views. But that gate is consent-gated, which means page views are counted only for visitors who accept analytics — the traffic number is biased toward consent-accepters. The repo documents this and offers the one-line change; it is a legal-posture decision, not a bug.

5.13 GDPR data rights

Export (Art. 20) produces a Zod-validated JSON bundle (version 1.0.0) covering the user, subscription, resumes with all revisions, applications, score snapshots, chat sessions and messages, chat usage, feedback and shares. Deliberately excluded: stripe_events_processed, OAuth tokens, sessions, and resume_variants.

Erasure (Art. 17) runs in order: cancel the Stripe subscription, delete the Stripe customer, tell PostHog to delete the user, write the hashed erasure_log row, then delete the auth user — whose cascades remove everything else. The log stores a SHA-256 of the user id rather than the id itself, so the audit trail is non-reversible while still proving a specific erasure happened at a specific time.

Two gaps: resume_analyses (the AI's critique of the user's resume) is excluded from the export without being listed in the documented exclusions, and score_snapshots.breakdown (added in migration 0013) is not exported either — only the older matchBreakdown and dynamicTips are.

6. The AI layer and model routing

Two independent fallback mechanisms, for good reasons

Parsers call generateObjectWithFallbacks in-process: iterate the model list, resolve the model, pick the schema form (strict JSON Schema only for openai/ and azure/ prefixes), and retry up to 3 attempts with 500 ms → 1s backoff. The error classifier is deliberately conservative — unknown errors are treated as permanent so a schema bug is not retried as if it were a network blip. A schema failure is recovered in place by pulling raw text off the SDK error, parsing it, converting null to undefined so Zod defaults fire, and re-validating — which returns without burning another model call.

Chat uses the gateway's own failover instead, because streaming has already begun by the time a model fails.

Ordering by measured reliability

This is the most valuable piece of AI engineering in the repo. A probe ran the real agent loop — unforced tool calls, the real inputSchema for every tool, the real 27 KB system prompt, five attempts per model, ground truth = the SDK's execute callback:

ModelEditedLeaksNarrationsMedian
anthropic/claude-haiku-5.55/5005.6s
amazon/nova-micro5/5002.7s
zai/glm-5.3-flash5/50023.0s
reflection/beam-free3/5008.2s
nvidia/nemotron-3.5-lightning-free3/5006.4s

Zero leaks and zero narrations across every model and attempt: the feared failure — a confident "Done, I changed it" with nothing changed — does not happen. Models that do not edit instead ask a clarifying question, which is the agent's designed needs-you behaviour. The chain was reordered by this table, not by price: nova-micro moved above a $0 model because it edits 5/5 and is the fastest caller.

The lesson worth keeping

The first version of this probe passed parameters where AI SDK 6 wants inputSchema. That made the tools schemaless, and the probe then reported that nova-micro "hard-errors 40% of the time" and that nemotron "never calls the tool". Both were artefacts. A measurement harness that differs from production produces confidently wrong results, and wrong measurements get acted on. The probe now mirrors the route's tool construction verbatim.

Standing rule, already in the code

Every price, latency and capability claim in lib/ai/providers.ts is a dated snapshot and rots. The file's own header records four occasions where a "free" model turned out to be 403 Free tier users do not have access, and instructs re-verification with npx --yes vercel@latest ai-gateway models endpoints <id> --format json. The rule is correct — but it depends on a human running it, and several of the numbers the free-tier margin argument rests on are three weeks old.

7.2 CI, build and deploy

What CI does today

  • One workflow: push to main and every pull request.
  • Node 22, pnpm from the packageManager field, --frozen-lockfile so a drifted lockfile fails the build.
  • pnpm typecheck then pnpm test, with a dummy POSTGRES_URL.
  • Concurrency group cancels in-progress runs per ref.
  • No secrets are used.

What CI does not do

  • No pnpm build. The root layout calls getUser(), which the build also evaluates, so the build needs a live Postgres or a build-time bypass. The consequence is that the route graph is never compiled on a PR.
  • No lint step — and no lint or format configuration exists in the repo at all.
  • No coverage gate, and the coverage include covers only components/schema-form/** and lib/** — app/, most of components/ and scripts/ are excluded from the report entirely.
  • No deploy job — deployment rides Vercel's own git integration.

Build and release mechanics

  • prebuild runs pnpm db:migrate, so production migrations are applied by the deploy, not by hand. A bad migration therefore fails at deploy time on main — after it has already been proven in dev, which is the intended ordering.
  • serverActions.bodySizeLimit: '10mb' supports PDF resume imports, matched by a server-side MAX_FILE_BYTES cap.
  • serverExternalPackages: ['@huggingface/transformers'] keeps the ONNX native binary out of the server bundle.
  • Sentry's build wrapper uploads sourcemaps only when SENTRY_AUTH_TOKEN is present.

Operational tooling

10. Findings register

Ordered by severity. Severity reflects user-visible or financial impact, not code aesthetics. Every finding was verified against the source by two independent passes, and the highest-severity ones were confirmed by direct inspection.

P0 Role Fit is a constant 5 points in every resume's score

Evidence. lib/scoring-async/score-hybrid.ts:93-100 passes { roleFitSimilarity: null }; lib/scoring/dimensions/role-fit.ts returns NEUTRAL_ROLE_FIT_SCORE = 50 with fallback: true; the sync path defaults to null as well. The async roleFitSimilarity() implementation is called only from tests.

Impact. Under WEIGHTS_V2 every resume gets a fixed 0.10 × 50 = 5.0 of 100 points. One of the seven advertised dimensions carries zero signal, the scorecard shows a flat bar, and no edit can move it. It also makes the demo-video beat "Role fit moves off 50" unfilmable, as the drift memo records.

Recommendation. Either call the existing roleFitSimilarity() from the hybrid wrapper (one line — the function exists and is tested), or set the dimension's weight to 0 and remove it from the scorecard. The first is better: the capability is already paid for.

P0 The chat agent can quote a different ATS score than the scorecard shows

Evidence. The page and the list both read the persisted snapshot through resolveRenderedBreakdown (app/(dashboard)/dashboard/resumes/[id]/page.tsx:150, lib/db/queries.ts:339). The chat route instead recomputes with the sync engine on every turn (app/api/chat/route.ts:311).

Impact. The two engines differ precisely where the hybrid engine is designed to disagree with token matching — ATS keyword evidence, content quality, intent coverage. So this is not a rare edge case; it is the normal case. A user asks "what's my score?" and gets a number that does not match the one on screen. This is the same class of bug the repo already fixed once (the list-badge divergence) and once more (the scorecard-tips contradiction) — two surfaces, one value, two implementations.

Recommendation. Route the chat's score read through resolveRenderedBreakdown, exactly as the other two surfaces do. The reason the chat recomputes (to reflect in-memory edits that have not yet been persisted) is real; the fix is to persist first, not to keep a third computation path. The repo already has the "one helper, both surfaces" pattern and the matching assertion test — apply it here too.

P1 The chat's own ATS tool can install a snapshot that makes the page fall back to the sync engine

Evidence. lib/chat/tools/get-ats-score.ts:116-121 calls recordScoreSnapshot without the breakdown field, so the row persists with breakdown: null (lib/db/queries.ts:1597). Both snapshot readers select the newest row.

Impact. After the chat computes a score, that snapshot becomes "latest". resolveRenderedBreakdown rejects it (no breakdown) and falls back to the sync engine — so the page renders a sync score while the snapshot row holds the hybrid number. The divergence returns, by a different route.

Recommendation. Pass breakdown in the tool's snapshot write. One line, and it closes the same door the recompute-flicker fix closed.

P1 A failed payment does not demote the local plan

Evidence. lib/payments/stripe.ts:243-290 persists the subscription on active|trialing and demotes on canceled|unpaid. A past_due event is not handled, so the row keeps plan='pro', status='active' and isProEffective stays true. invoice.payment_failed is not in the handled event list either.

Impact. A user whose card fails keeps Pro access indefinitely. The code comment in lib/billing/types.ts:83-85 states the opposite intent ("We demote to Free immediately"), so this is an implementation gap against a documented decision rather than a policy choice. Direct financial exposure, small but real — and it also means the free-tier revenue is overstated.

Recommendation. Write past_due, incomplete, incomplete_expired and paused through the same demotion branch, and handle invoice.payment_failed.

P1 CI never compiles the route graph, and the repo has no linter

Evidence. .github/workflows/ci.yml:45-58 runs typecheck and tests; pnpm build is a commented-out TODO because the root layout calls getUser() at build time. There is no lint configuration and no lint script in package.json.

Impact. A route that references a non-existent export, or a server-component boundary violation, typechecks fine and passes unit tests but fails at deploy — where prebuild also runs the production migration, so a build failure becomes a migration-plus-build incident on main. For a solo operator this is the single most expensive class of avoidable failure.

Recommendation. Add a build step to CI behind a build-time DB bypass (a stub getUser when SKIP_DB_DURING_BUILD is set). Add ESLint with eslint-config-next and wire it into CI. Both are small, and both convert a deploy-time surprise into a PR-time comment.

P2 Liveblocks and Inngest are in the stack, the runbook and the plan constants — but do nothing

Evidence. lib/liveblocks/server.ts is 13 lines and imported by nothing — the pricing page says so explicitly. lib/inngest/client.ts defines exactly one function, testEvent, on an app/test trigger. Both appear in .env.example, in the AGENTS.md "locked stack", and in the production runbook. PLANS.pro.canCollab is true and PLANS.pro.canOptimize is read by nothing.

Impact. The pricing page and the plan constants advertise a capability that does not exist. The schema comment promising a periodic prune of stripe_events_processed has no implementation, so that table grows without bound. And two paid services sit in the environment adding cost and attack surface for zero function.

Recommendation. Either ship the collaboration slice or remove Liveblocks from the stack and the pricing copy. Inngest is cheap to keep if the first real job lands — the score recompute is the obvious candidate — but the app/test function should not be the only one. If Liveblocks is deferred, canCollab should not be true.

P2 The applications / resume_variants pipeline is a third path through the domain that nothing exercises

Evidence. applications has a complete query layer and an actions file (app/(dashboard)/dashboard/applications/actions.ts) but no page renders it. resume_variants is written only by scripts/seed-demo.ts, and listResumeVariants has no callers. The variant flow actually works through resumes.parentResumeId.

Impact. Two tables, a query layer and a route-actions file that cost maintenance and confuse the model of the product. resume_variants.matchScore and matchBreakdown duplicate data that now lives in score_snapshots.

Recommendation. Decide: build the Applications board (which would make the pipeline live and give the product a real "I applied to this" surface) or delete the tables and the query layer. Leaving both paths is the worst option, because a future reader cannot tell which one is canonical.

P2 Six documentation artefacts disagree with the tree

Evidence.

  • Test counts: README.md:37 says 970/78 files; AGENTS.md says 2,205; the tree has 172 files / ~1,970 cases.
  • docs/setup/production.md:32 and :762 say migrations 0000–0008; there are 14 (0000–0013).
  • posthog-ai-observability-report.md:35 says posthogPrivacyMode: false; lib/ai/providers.ts:647 sets it true — the code is the privacy-safe one, the report is wrong.
  • ADR 0002 describes an auto-print preview flow that no longer exists.
  • The WEIGHTS_V2 doc comment says the weights are 0.68/0.32; the constants are 0.70/0.30. The constants are correct and sum to 1.00.
  • The template gallery's docstring says "Five templates today"; there are six.

Impact. Individually trivial; collectively they make the documentation untrustworthy in exactly the places a new contributor (or a new session of this agent) looks first. The migration range is the dangerous one, because it answers "what is in production?" incorrectly.

Recommendation. One drift sweep. Generate the test count and the migration range from the tree rather than typing them.

P2 Server-side analytics fire regardless of consent

Evidence. The consent gate wraps the client SDKs. lib/posthog/server.ts is used by 22 call sites — the share route, resume CRUD, scoring, chat, subscriptions — and none of them consult the consent record.

Impact. A visitor who declines analytics still has their resume created, shared, scored and chatted about recorded server-side. Whether that is a GDPR problem depends on whether server-side product analytics count as "analytics" under the policy the legal pages describe — which is a legal-posture question, not an engineering one. It should at least be a deliberate, documented decision rather than an accident of where the gate was mounted.

Recommendation. Decide explicitly, then make the code match: either gate server-side events on the stored consent, or state in the privacy policy that operational analytics are collected on the server irrespective of the browser-level choice, and why.

P2 Unreachable code that the product's design implies should be reachable

Evidence. restoreRevision and listRevisions (lib/db/queries.ts:661, 692) have no callers — the revision history the schema was built for is invisible. erasure_log is written but never read — no admin or audit surface consumes it. resume_analyses is excluded from the GDPR export without being listed among the documented exclusions. score_snapshots.breakdown (migration 0013) is not exported either. The verification table has no FK to user, so password-reset tokens survive account deletion.

Impact. The revision history is the natural home for "restore this version" — a feature the editor's undo (localStorage, 50 entries, per-device) cannot fully replace. The erasure log is the evidence trail for a compliance claim the legal pages make. The export gaps mean a user requesting their data does not receive all of it.

Recommendation. Small, high-value additions: a "restore this revision" affordance in the editor, an export that includes resume_analyses and breakdown, and a FK from verification to user with a cascade.

P3 Assorted sharp edges

  • Stripe price id unset ⇒ every live subscription is recorded as free (lib/payments/stripe.ts:240-241 compares against null). Defensive, but it fails silently in the wrong direction.
  • Stripe redirect URLs read BASE_URL directly while the rest of the app resolves NEXT_PUBLIC_APP_URL → BASE_URL via lib/site.ts. Two origins, one source of truth wanted.
  • PLANS lives in lib/db/schema.ts and PlanId is defined twice (lib/db/schema.ts:201 and lib/billing/types.ts:17). A drift magnet; move one and the other silently disagrees.
  • sentry.client.config.ts is imported by nothing. It configures session replay at 100% on error; if it is ever loaded, that is a privacy posture change nobody made consciously.
  • The share-status view object is declared three times (the variant page, the preview page, and the canonical type in the share button) instead of once.
  • Print settings are computed twice in the preview page (:150 and :152) — same call, two invocations.
  • The template field has two writers that do not share a path: the editor's form pipeline and the chat tool's saveResumeRevision.
  • The chat token cap is a soft cap — usage is written after the stream drains, so a user can overshoot by roughly one turn. This is deliberate and documented, and the right trade against holding a row lock across a model call. Noted here only so it is not mistaken for a bug.

What is not a finding

For the avoidance of doubt, these were checked and found sound: the deterministic share token (a derivation, not a secret; the key lives in the environment, so a DB dump yields no usable URLs); the composite PK on chat_usage; the Turnstile site key being server-read; the stripe event marking happening after success; the Sentry data-collection hardening; the consent predicate being shared by both analytics gates; the rich-text overlay's drop-don't-misapply rule; the sync/async engines composing through one function; and the strict-schema peeling of .default() wrappers for OpenAI-compatible providers.

C. Glossary

TermMeaning
EnvelopeThe resume document: sections (plain strings) plus metadata and the optional formatting overlay. Stored as JSONB in resume_revisions.data. It is not a table.
Master / variantA master is the candidate's source-of-truth resume. A variant is a resumes row with is_master = false and a parent_resume_id. They share the same revision machinery.
JevTypeSafe's probabilistic judgment API, reached through the Vercel AI Gateway with zero data retention. It classifies JD requirements and scores evidence depth. Version-pinned as jev-1.14.0.
Sync vs hybrid engineTwo ways to fill the same scoring inputs. Sync is deterministic (tokens, BM25, regex). Hybrid adds local MiniLM embeddings and Jev evaluation. Both compose through composeOverallScore().
SnapshotA persisted score result (score_snapshots) holding the headline score, the full breakdown and the dynamic tips, written in the same pass as the computation.
Gateway-native failoverDelegating model fallback to the AI Gateway via providerOptions.gateway.order, rather than iterating models in-process. Necessary for streaming, where bytes have already reached the client.
Drift memoThis repo's decision log for changes that diverge from a plan or ADR. Thirty-plus of them, each recording what changed, why, and what it costs.
